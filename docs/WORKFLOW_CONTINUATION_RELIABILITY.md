# 검색 이후 작업 진행 중단 분석

2026-09-13~14 및 9월 21일, 삼성 SM-F731N/API 37, 배달의민족 16.22.0에서 `피자 주문해 줘`를 재현했다. 이번 요청은 실제 주문을 넣는 것이 아니라 검색 이후 관찰·진행 문제를 진단하는 작업이다.

## 핵심 원인: 화면 수집 실패가 아닌 계획·완료 계약 충돌

검색 이후 Sonju는 99개 요소를 수집했다. `treeTruncated=false`였으며 가게 이름, 메뉴, 최소주문금액, 배달팁과 실제 CLICK을 제공하는 가게 카드가 있었다. 이름은 비클릭 자식 노드이고 카드 부모는 클릭 가능했다. 검증 가능한 화면 데이터가 이미 제공된 상태였다.

수정 전 계획 프롬프트에는 음식 종류만 주어지면 검색까지만 진행하고, 여러 식당·메뉴 중 하나를 고르지 않은 채 멈추라는 지침이 있었다. 반면 원래 최종 목표는 `피자 주문해 줘`로 고정되고, 주문 완료 검증은 검색 결과나 가게 목록을 주문 완료로 인정하지 않았다.

모델은 이 지침에 따라 FINISH 또는 검색 결과를 근거로 한 완료를 반복 제안했다. 실행기는 원래 주문 목표가 충족되지 않았으므로 거절했다. 기본 재현에서 97.5초 동안 모델 요청이 14회 발생했으며, 검색 이후 가게 상세로 진입하지 못했다. 로그에는 `goal evidence rejected checks=3 matched=3`, 이후 `checks=4 matched=4`가 반복됐다. 값과 노드는 일치했지만 최종 작업이 끝나지 않은 상태였다.

반복을 악화시킨 두 가지 코드 결함도 있었다.

- 모든 근거가 일치해도 모델에는 ‘완료 근거가 현재 화면과 일치하지 않는다’는 잘못된 피드백을 보냈다. 작업 단계의 문제를 관찰 오류처럼 설명했다.
- 해당 실패를 기록할 때 snapshot을 넘기지 않았으며, `recordPlanningRejection`도 FINISH만 있는 제안을 버렸다. 실행 없는 완료 제안이 반복 실패 추적에서 빠졌다.

근거는 `app/build/reports/completion-qa/pizza-order-observation-before/`의 `flow.log`, `during.xml`, `screen.xml`, `result.json`에 있다.

## 공통 경로 수정

1. **원래 목표와 준비 단계 분리** — 검색을 전체 주문·예약·변경의 완료로 바꾸지 않는다. 명시한 사용자 조건을 우선하고, 조건이 없으면 현재 기본 정렬에서 요청에 맞는 후보 상세를 확인한다. 가능한 탐색을 최종 결제 제한 때문에 미리 중단하지 않는다. 확인하지 않은 선호·가격·필수 정보를 만들거나 기존 장바구니를 비우지 않는다.
2. **가게·상품 텍스트와 실제 클릭 대상 연결** — `PlannerObservation`이 공개 자식 라벨에 `click_target=node=…`를 붙인다. 기존 `UiTargetResolver`가 찾은 관찰된 부모만 사용하며 숨겨진·비활성·민감 컨트롤은 노출하지 않는다. 부모가 요약에서 생략돼도 라벨과 실행 대상을 연결할 수 있다. 실행은 계속 실제 verifier-issued `VerifiedPlan`을 요구한다.
3. **정확한 완료 거절 피드백** — 근거 값 일치 여부와 최종 목표 충족 여부를 구분한다. 이미 끝낸 검색을 반복하는 대신 현재 관찰에서 가능한 다음 상세·준비 단계를 제안하도록 한다.
4. **실행 없는 종료 반복 제한** — snapshot과 FINISH 제안을 실제 실패 기록에 포함한다. 같은 관찰 상태에서 실행 없이 종료 제안이 세 번 거절되면 미완료라고 명확히 알리고 멈춘다. 실제 실행을 시도하거나 다른 화면으로 진행한 뒤에는 과거 종료 제안을 계속 누적하지 않는다.
5. **원문 검색과 자동완성 구분** — 후속 기기 검사에서는 `피자` 입력 뒤 자동완성 `피자헛`을 선택해, 요청하지 않은 브랜드의 준비중 가게 하나로 범위가 좁아졌다. 검색어 입력 직후에는 다른 추천어로 범위를 바꾸기 전에 원문 검색을 실행하도록 검증한다. 원문과 같은 제안, 실제 검색 버튼, 사용자가 명시한 브랜드는 구분한다. 이미 제출을 시도한 뒤의 정상적인 결과 탐색은 허용하며, 모델이 임의로 추가한 제한 때문에 이용 가능한 후보가 없어지면 원래 요청 범위로 복구하도록 한다.

주문 완료 조건이나 결제 차단은 낮추지 않았다. 후보가 여러 개라는 상황과 실행할 UI 컨트롤을 하나로 식별하지 못하는 상황도 구분한다. 특정 가게·상품·앱 패키지·웹사이트를 선택하는 분기는 추가하지 않았다.

## 후속 기기 검사에서 확인한 관찰·탐색 문제

첫 수정 후 같은 명령은 실제 가게 상세와 피자 메뉴·가격·옵션 화면까지 진행했다. 이 과정에서 두 가지 추가 취약 경로를 확인했다.

- **오래된 전환 화면 재사용:** 가게를 연 뒤 11개 요소의 전환 화면이 재사용됐고, 모델은 스크롤 대상을 찾지 못했다. 다음 새 관찰에는 67개 요소와 실제 메뉴 정보가 있었다. 캐시는 2초 이내라는 이유만으로 앱 이벤트 후에도 재사용될 수 있었다. 이제 현재 앱의 epoch가 같고 로딩 중이 아닌 관찰만 재사용한다. 화면이 움직이더라도 새 수집 자체는 기존의 유한한 수집·재검증 경로로 처리한다.
- **스크롤 방향과 전체 작업 위험도 혼동:** 재검사에서 영업 종료 가게가 열렸고, 사진·리뷰·추천 가게 영역은 LEFT/RIGHT만 제공했다. 모델의 SCROLL_DOWN은 이 세 가로 영역을 같은 후보로 취급했고, 주문 과제의 높은 위험도 때문에 `Blocked`로 종료됐다. 이제 실제 지원 방향을 grounding 조건에 포함한다. 스크롤 대상이 여럿이면 실행하지 않고 `NeedsReplan`으로 정확한 target을 요청한다. 최종 확정이나 다른 고위험 클릭의 모호함을 허용하는 변경은 아니다.

요청한 조건에서 영업 종료·품절 등으로 이용 불가능한 후보는 다른 관찰된 이용 가능 후보로 탐색하도록 계획 지침도 보강했다. 없는 주문 버튼이나 메뉴를 만들어내지 않는다.

후속 실패는 `completion-qa/pizza-order-observation-final/`에 보존했다. 파일 이름의 `final`과 무관하게 이 기록은 마지막 보강 **전**의 실패 자료이며 성공 근거가 아니다.

## 2026-09-21 재연결 검사: 불완전한 전환 화면 재수집

9월 14일 APK를 삼성 기기에 설치하고 로컬/설치 APK의 SHA-256 일치를 확인한 뒤 같은 주문 명령을 다시 실행했다. 배민 홈 팝업을 지나 검색 화면에 도달했으나, 전환 도중 수집한 44개 요소의 snapshot이 `treeTruncated=true`였다. 기존 수집 재시도 조건은 화면이 비어 있거나 epoch가 달라진 경우만 처리했으므로, 텍스트가 있는 불완전한 화면을 바로 계획에 넘겼다. 주문 과제의 verifier는 이 화면에서 SET_TEXT를 차단했다. 같은 시각의 후속 관찰은 47개 요소의 온전한 트리였으므로 지속적인 접근성 미제공 상태와 구분된다.

`ScreenContextHandoff.shouldRetryCapture`의 공통 조건에 불완전한 트리를 추가했다. 계획용 수집과 실행 직전 수집 모두 기존 횟수·간격 안에서 새 root를 다시 읽는다. 고위험 동작의 불완전한 트리 차단과 실행 직전 검증은 유지한다. 회귀 검사는 라벨이 충분해도 불완전한 트리를 재수집하고, 정상 관찰에서는 즉시 진행하며, 재시도 한도를 넘지 않는지 확인한다. 수정 전 기록은 `completion-qa/pizza-order-reconnected-20260921/`에 보존했다.

재빌드·설치 후 검색 입력 화면에서 원래 명령을 다시 실행했다. SET_TEXT로 `피자` 입력 → SUBMIT_TEXT의 실제 IME SEARCH(action=3) → 검색 효과 확인 → 결과 가게 클릭 → 가게 상세·검색한 메뉴까지 40.0초에 도달했다. 모델 호출은 4회였고 입력·제출·대기·가게 클릭이 각각 한 번 실행됐다. 담기 전에 중단했다. 첫 재현의 홈 팝업 단계까지 새 APK로 다시 반복한 검사는 아니다.

당시 오전 검색 결과에서 연 가게는 이삭토스트 성남분당야탑점이며, 화면에는 `베이컨 포테이토 피자` 메뉴와 6,500원이 있었다. 이 검사의 성공 범위는 원문 검색과 검색 이후 가게·메뉴 화면 진입이다. 피자 전문점 선택이나 주문 내용의 적합성, 주문 완료를 검증한 것으로 확대하지 않는다. 이 경로에서는 영업 종료 가게를 만나지 않았으며, 이용 불가능한 후보에서 대안을 고르는 검증은 앞서 통과한 단위·실제 모델 검사와 구분한다.
