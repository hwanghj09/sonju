# 저장된 스킬이 없는 명령의 실행 신뢰성

2026-09-09. 기존 작업 폴더의 미커밋 변경을 보존하고 일반 명령 경로를 개선했다.

## 판단 근거

손주의 목표에는 새로운 앱과 새로운 요청을 현재 화면에서 해석하는 능력이 필요하다. 이 구현에서는 기존 `gpt-5.6-luna`와 접근성 우선 구조를 유지하고, **목표에 맞는 관찰 → 한 행동 → 실제 결과 검증 → 실패를 반영한 재계획**을 강화했다. 성공한 경로는 기존 AppSkill 학습으로 재사용한다.

조사에 참고한 일차 자료:

- [Google Research AndroidWorld](https://github.com/google-research/android_world): 동적 작업과 실제 앱 상태에 근거한 평가 환경. 모델의 응답이나 행동 시퀀스 자체보다 최종 작업 상태를 검사하는 평가 방식을 참고했다.
- [DailyDroid 연구](https://arxiv.org/abs/2604.17817): 화면 텍스트와 스크린샷 입력을 비교하고 접근성·입력 방식·앱 설계의 실패를 분석한다. 모든 단계에 이미지를 추가하는 것만으로 해결된다고 가정하지 않았다.
- [MobileWorld](https://arxiv.org/abs/2512.19432): 사용자 상호작용과 도구 연계를 포함한 모바일 작업을 평가한다. 인증과 모호한 선택의 사용자 인계는 기존 제품 경계로 유지했다.
- [Android AccessibilityService API](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService): 노드 action, 창 관찰, screenshot capability의 실제 플랫폼 제약을 기준으로 했다.
- [OpenAI 이미지 입력 문서](https://developers.openai.com/api/docs/guides/images-vision): 좌표 작업의 이미지 크기와 전처리, 공간 위치 추론의 한계를 확인했다. 일반 접근성 계획의 저지연 설정은 유지하고 원본 이미지 계획에만 `reasoning.effort=low`, 최대 출력 3,200토큰과 25초 읽기 제한을 적용했다.

이 자료는 설계 선택의 근거이며 손주의 성공률 측정값이 아니다. 모델 교체나 학습 데이터 확대의 효과는 이번 변경에서 비교 실험하지 않았다.

## 확인한 실패 경로와 적용

| 확인한 제약 | 적용한 변경 |
|---|---|
| 기존 화면 요약은 조작 가능한 노드를 우선한 90개 제한 때문에 긴 목록에서 결과 본문을 생략할 수 있다. | `PlannerObservation`은 요청과 관련된 노드, 입력/상태, 본문·제목을 함께 보존한다. 원래 path를 유지하고 생략 수를 알리며, 이름 없는 컨테이너에는 실제 하위 레이블을 제공한다. |
| `SUBMIT_TEXT`가 모델 도구 목록에서 제외되어 입력 후 키보드 검색을 실행할 수 없었다. | 사용자 요청에 포함된 검색어, 현재 입력값 일치, 검색 필드의 실제 식별자/힌트, `IME_ENTER` 지원을 결정적으로 검사한 뒤 허용한다. 일반 메시지·댓글·인증 입력란에는 허용하지 않는다. |
| 모델에 노출된 `OPEN_URL`은 실제 verifier에서 검토된 병원 주소 외에는 차단된다. | 일반 모델 도구 목록에서 제외했다. 웹 검색은 실제 브라우저 검색 UI를 사용하고, 기존 병원 주소는 로컬 전용 경로를 유지한다. |
| 실행 전 거절된 후보의 행동 정보가 모델의 반복 실패 이력에 남지 않았다. | 현재 의미 화면에 연결한 후보/거절 이유를 최근 문맥에 포함한다. 두 번 실패한 동일 행동은 실행 전에 걸러 다른 계획을 요청한다. 입력값 수정은 별개 시도로 구분한다. |
| 숫자를 제거하는 스킬용 fingerprint를 반복 판정에 사용하면 숫자 입력의 실제 진행을 순환으로 오인할 수 있다. | 실제 관찰 fingerprint와 실행 결과로 순환을 검사한다. 서로 다른 복구 시도를 할 여지를 주되 24개 도구·24회 모델 호출·3분과 무진행 제한은 유지한다. |
| 모델이 `WAIT`에 `continue_after_action=false`를 반환하면 중간 대기 후 완료 처리로 빠질 수 있다. | 미완료 모델 계획은 항상 다음 관찰을 요구한다. 완료는 계속 `goalSatisfied`의 화면 근거 검사로 판정한다. |
| WebView/Canvas의 구조가 그대로인 채 픽셀만 바뀌면 기존 “의미 화면당 이미지 1회” 규칙이 다음 단계를 막는다. | 의미 화면과 실제 이미지 digest를 함께 사용한다. 실패한 캡처는 예산을 쓰지 않는다. 초기 이미지 호출은 2회, 이후는 시각 행동의 postcondition과 변경된 이미지가 검증된 경우에 한 번씩 허용하며 요청당 최대 6회다. |
| 실 API 테스트 중 세로 화면의 좌표를 잘못 정규화한 응답이 발생했다. | 원본 이미지의 가로·세로 크기를 전달하고 축별 좌표 계산을 명시했다. 원본 이미지 계획에는 제한된 추론을 사용한다. 좌표 정확도는 별도 검증 항목으로 남긴다. |
| 실기기의 일반 계산 키패드에서 숫자 버튼 세 개가 CVC 입력칸으로 오인되어 32개 노드 중 24개가 민감 정보 처리되었다. | 같은 컨테이너의 0–9, 사칙연산, 등호 버튼이 모두 관찰된 경우에만 숫자 버튼을 공개 계산 컨트롤로 분류한다. 계산 입력·결과의 숫자 역시 이 구조와 의미가 확인될 때만 보존한다. 숫자만 있는 PIN 키패드, 인증 문구, 비밀번호 필드의 보호는 유지하며 앱 패키지 예외는 추가하지 않았다. |
| 실행 직전 레이블 비교에서 2글자 미만 토큰을 버려 숫자 `1` 같은 버튼이 같은 노드여도 거절되었다. | 정규화한 전체 레이블의 정확한 일치도 인정한다. 창·위치·클래스·민감 여부와 대상 유일성 검사는 그대로 거친다. 다른 숫자나 기호는 일치로 취급하지 않는다. |
| 실제 계산 입력은 성공했지만 접근성 텍스트가 `계산기 입력란 146 곱하기 23`처럼 기호를 풀어 읽어 요청값과 다른 것으로 판정되었다. | 공개 계산 입력의 명시적인 안내 문구, 읽어 주는 사칙연산 이름과 동등한 연산 기호를 정규화한 뒤 식 전체를 비교한다. 임의 부분문자열이나 계산 결과의 수학적 동치로 성공을 추정하지 않는다. |

## 실행 경계

모델은 실행 후보를 제안한다. `DeterministicActionVerifier`가 현재 화면의 유일한 노드와 revision에 묶인 `VerifiedPlan`을 발급한 뒤 접근성 서비스가 실행한다. 민감 화면의 원격 이미지 전송, 개인정보·인증정보 입력, 결제·송금 최종 확정 제한은 유지한다. 이미지 digest 일치는 관찰 일치의 근거이며 사용자 목표 달성 자체의 근거로 취급하지 않는다.

## 검증

수정 전 연결된 삼성 SM-F731N에서 `계산기에서 137 곱하기 24 계산해줘`를 실행했을 때 `SET_TEXT` 후 `POSTCONDITION_TIMEOUT`, 입력란 `CLICK` 후 재차 `POSTCONDITION_TIMEOUT`, 이어서 작업 중단을 관찰했다. 설정의 글자 크기 메뉴 탐색에서는 AI 노드 클릭이 실행 직전 갱신으로 한 번 실패한 뒤 재계획으로 이동했다.

회귀 테스트는 긴 목록의 본문 보존, 민감·비표시·기기 내 OCR 내용 제외, 일반 검색과 메시지 제출 구분, 값이 변하는 키패드 입력, 반복 후보 차단, 무진행 한도, 동일 의미 구조의 시각 진행과 최대 호출 한도, 완료 근거 검사를 포함한다.

별도의 opt-in 실 API 테스트는 저장된 스킬이 없는 가상 도서관에서 검색 열기 → 검색어 입력 → 키보드 검색 제출 → 상세 화면 → 출판사 확인을 수행한다. 매 행동은 실제 verifier를 통과한다. 이는 합성 화면과 실제 모델의 통합 검증이며 실제 Android 앱 조작과는 구분한다.

- `assembleDebug`, `lintDebug` 성공. Lint 오류 0개, 경고 80개.

이 검증은 제한된 실제 명령 사례다. 전체 앱·전체 음성 명령의 성공률이나 모든 OEM의 동작을 증명하지 않는다. 음성 인식 정확도는 재측정하지 않았으며, 기기 실행에는 인식된 문장을 전달하는 기존 음성 명령 Intent를 사용했다. 인증·결제는 시험하지 않았다. 배포 직후 접근성 재연결과 기존 직접 확인 대기의 복원도 별도의 제품 E2E 검증 항목으로 남는다. 다음 평가는 저장 스킬이 없는 다양한 앱·목표에서 최종 상태 성공률, 시간, 모델 호출 수, 사용자 인계 비율을 반복 측정해야 한다.
